## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R1 | Selecting a different option on an answered question replaces the previous selection immediately, with no extra confirmation step. | Same, until the question has been submitted for feedback; after feedback is shown the answer is locked. | Conflict with another requirement: R6 and R7 reveal the correct answer after feedback. If the answer could still be changed afterwards, the user could simply switch to the right option and the quiz result would be meaningless. The user need (change my mind freely, no extra step) is kept for everything before feedback. |
| R5 | Selected answers are preserved if the quiz view is reloaded or interrupted before submission. | Selected answers are not lost when the user moves between questions or opens the Confirm review. They live in memory for the life of the quiz prompt; surviving an app restart is not required. | Not feasible as stated. The quiz runs in a terminal UI whose state is in memory only; there is no page reload and no persisted quiz state to restore. Interviewee C-6 / C-8's real need was not losing picks while switching around and being unsure whether progress is safe, which the revision keeps. |
| R6 | The results view shows, for every question, the options, the answer the user selected, and the correct answer. | When a question is submitted for feedback, the quiz shows whether the pick was correct, the correct option and the explanation, next to the options and the user's pick. | Cannot be checked as written: the quiz has no single "results view" to inspect; feedback is shown one question at a time. The interviewee's need (tell my own mistake from a quiz bug, see the correct answer) is kept at the per-question level, where it can be checked. |
| R7 | After submitting, the results are shown immediately, without waiting for any further action. | When the user submits a question for feedback (key `s`), the result is shown in the same interaction, with no further step and no waiting. | Cannot be checked as written: "submitting" and "the results screen" are ambiguous in this app (per-question feedback versus final submit of all answers). The revision pins "submit" to the action that produces results. |

## Triage notes (Step 3)

- R4: the TUI did not show any count of answered questions (tabs only mark answered questions). This was a code gap, not a wrong property, so I fixed the code: the Confirm tab now shows `Review (n/N answered)`, computed by `answeredCount` in `question-answers.ts`.
- R1, R2, R3: the answer logic lived inline in the Solid component. I moved the pure parts (`pickAnswer`, `answeredCount`, `replyAnswers`) into `question-answers.ts` and the component now calls them, so the properties test the code that actually runs.
- Add any further failures you hit when you run the properties here, with the shrunk counterexample and whether the fix was in the code, the test, or the requirement.
- CI: adding `@opencode-ai/tui#test` made CI run the whole tui suite for the first time. The first `test/unit` run failed on an unrelated, timing-sensitive rendering test (`DiffViewerFileTree`) and a re-run then failed on two unrelated opencode-package timing tests. All three passed locally and on re-run, so I treated them as flaky tests, not code or requirement problems, and left them unchanged.
- CI: the tui `test` script used `--only-failures`, which hides passing tests, so the CI log did not show the properties running. I removed that flag from the tui package only, so passing tests, including R1 to R4, R6 and R7, are listed in the log.
